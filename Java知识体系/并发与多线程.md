# 并发与多线程

## 并发包核心类

- AQS
  - CLH队列实现
    - AQS 通过 `volatile int state` + CLH 变体双向队列维护等待线程。
    - `head` 为哨兵节点，`tail` 指向队尾，竞争失败线程封装为 `Node` 入队。
  - 性能为什么高？
    - CAS + `volatile` 避免重锁竞争，失败线程才阻塞。
    - 采用“先自旋短等待，再阻塞”的策略，降低频繁上下文切换开销。
    - 队列化唤醒（`unparkSuccessor`）减少惊群。
  - 入队列过程？
    - 首次竞争锁失败 -> 创建节点 -> 自旋 CAS 尝试挂到 `tail`。
    - 入队后检查前驱是否是 `head`，若是则尝试再次获取锁；否则决定 `park`。
    - 释放锁后由前驱节点负责唤醒后继。
    - 为什么要先自旋？
      - 临界区很短时，自旋可能在一次调度周期内拿到锁，避免 park/unpark 的系统调用成本。
- Semaphore
  - 限流可用？
    - 可用。`Semaphore permits` 本质是并发配额控制，常用于“最多 N 并发请求”。
    - 适合单机限流；分布式限流应配合 Redis/网关令牌桶方案。
- ReentrantLock
  - 与Synchronized区别？
    - `ReentrantLock` 支持可中断获取（`lockInterruptibly`）、超时获取（`tryLock(timeout)`）、公平锁、多个 `Condition`。
    - `synchronized` 语法级，自动释放锁，JVM 优化深，简单场景可读性更高。
  - 释放阻塞的指定线程？
    - 锁本身不能“指定线程解锁”。可通过不同 `Condition` 分组等待线程，再 `signal` 定向唤醒某一组。
  - 为什么finally释放？
    - 防止异常路径导致锁泄漏，否则其余线程永久阻塞，形成活锁/死锁风险。
- 读写锁
  - `ReentrantReadWriteLock` 允许读共享、写互斥，适合“读多写少”。
  - 写饥饿风险可通过公平策略缓解，但吞吐会下降。
- CyclicBarrier / CountDownLatch
  - `CountDownLatch` 一次性门闩，计数归零后放行，不能重置。
  - `CyclicBarrier` 可循环使用，适合多线程分阶段汇合。
- LockSupport
  - 阻塞细节？
    - `park/unpark` 基于“许可(0/1)”语义，`unpark` 可先于 `park` 调用。
    - 每线程最多一张许可，不会累加；是 AQS、JUC 锁阻塞的底层基础。
- CopyOnWrite容器用途？
  - 读多写极少且可接受写时复制成本的场景，如配置快照、订阅者列表。
  - 写入会复制数组，内存与写延迟成本高，不适合高频写。
- UnSafe类用途？
  - 提供 CAS、内存屏障、直接内存访问、对象字段偏移等底层能力。
  - JDK 内部大量使用；业务代码优先用 `VarHandle`、`Atomic*`、`LockSupport` 等安全抽象。
- Callable与Runnable区别？
  - `Callable<V>` 有返回值、可抛受检异常；`Runnable` 无返回值且不能直接抛受检异常。
  - 提交到线程池后，`Callable` 对应 `Future<V>` 可拿结果。
- CompleteFuture使用？
  - 应为 `CompletableFuture`。用于异步编排：串行（`thenApply`）、并行汇聚（`allOf`）、异常恢复（`exceptionally`）。
  - 生产中建议显式传入业务线程池，避免默认公共线程池被阻塞任务拖慢。

## synchronized

- ReentrantLock区别?
  - `synchronized` 自动加解锁、结构简洁；`ReentrantLock` 功能更全、控制更细。
- 锁的量级
  - 什么是锁升级？
    - HotSpot 中常见路径：无锁 -> 偏向锁（JDK 15 后默认移除）-> 轻量级锁 -> 重量级锁。
    - 目标是“低竞争走轻路径，高竞争再膨胀”。
  - 如何降级？
    - 锁不会按线程实时“主动降级”。JVM 在后续竞争形态变化时，可能对新对象实例走更轻路径。
    - 工程上“降级”通常指减少锁粒度、缩短临界区、读写分离。

## volatile

- 共享一致性
  - MESI协议
    - CPU 缓存行四态：Modified/Exclusive/Shared/Invalid，用于多核缓存一致性。
  - 内存屏障实现
    - `volatile` 写前后插入 Store 屏障，读前后插入 Load 屏障，约束重排序并保证可见性。
  - 总线风暴
    - 高频写共享变量会导致缓存行频繁失效与一致性通信放大。
    - 典型优化：减少共享写、分段热点、`LongAdder` 替代高冲突 `AtomicLong`。

## 线程池

- 回收策略哪些？
  - 非核心线程：空闲超过 `keepAliveTime` 回收。
  - 核心线程：默认不回收；开启 `allowCoreThreadTimeOut(true)` 后也可回收。
- 调度算法有哪些？
  - `ThreadPoolExecutor` 本身是“任务提交 + 队列 + 工作线程”模型，不是严格时间调度器。
  - 定时类由 `ScheduledThreadPoolExecutor` 基于延迟队列调度。
- 几个核心参数含义？
  - `corePoolSize`：常驻线程数下限。
  - `maximumPoolSize`：线程总上限。
  - `keepAliveTime`：空闲线程存活时长。
  - `workQueue`：等待队列。
  - `threadFactory`：线程创建策略。
  - `RejectedExecutionHandler`：拒绝策略。
  - 阻塞队列有哪些？
    - `ArrayBlockingQueue`（有界数组）、`LinkedBlockingQueue`（链表，可近似无界）、`SynchronousQueue`（不存储元素，直接移交）。
  - 核心线程如何回收？
    - 默认不回收；调用 `allowCoreThreadTimeOut(true)` + 核心线程空闲超时才会回收。
  - 超过最大线程数会怎样？
    - 不会再创建线程，触发拒绝策略：`Abort`/`CallerRuns`/`Discard`/`DiscardOldest` 或自定义。
  - 为什么要有阻塞队列？
    - 平滑突发流量、削峰填谷，避免瞬时创建过多线程导致调度抖动。
  - 为什么避免用Executors静态线程池？
    - `newFixedThreadPool`/`newSingleThreadExecutor` 默认队列近似无界，易 OOM。
    - `newCachedThreadPool` 线程上限极高，易线程爆炸。生产应手动 new `ThreadPoolExecutor`。
- 调优
  - 大量RPC调用怎么调？
    - I/O 密集：线程数可高于 CPU 核数（常见 2~4 倍起测）。
    - 设置有界队列 + 超时 + 熔断 + 舱壁隔离，优先保障核心链路。
  - 大量计算任务怎么调？
    - CPU 密集：线程数接近 CPU 核数（N 或 N+1）。
    - 降低上下文切换，避免在计算线程中做阻塞 I/O。
- 线程生命周期有哪些？
  - `NEW`、`RUNNABLE`、`BLOCKED`、`WAITING`、`TIMED_WAITING`、`TERMINATED`。
  - 几个状态的转换？
    - `start()`：`NEW -> RUNNABLE`
    - 竞争监视器失败：`RUNNABLE -> BLOCKED`
    - `wait/join/park`：进入 `WAITING/TIMED_WAITING`
    - 任务结束：`RUNNABLE -> TERMINATED`
  - Thread.yield()含义？
    - 提示调度器“我可以让出 CPU”，不保证生效，也不释放锁。

## 其它考点

- 线程与进程/协程的区别？
  - 进程是资源分配单位，线程是 CPU 调度单位；协程是用户态轻量调度单元。
  - 协程切换成本低，但遇阻塞系统调用仍可能阻塞线程（取决于运行时）。
- 如何传递线程私有变量？
  - `ThreadLocal` / `InheritableThreadLocal`；在线程池中必须及时 `remove` 防止脏数据与泄漏。
- forkjoin
  - 分治并行框架，工作窃取队列提升 CPU 利用率；适合可拆分、纯计算任务。
- 生产者消费者
  - Object wait与Sleep区别？
    - `wait` 释放锁并进入等待队列；`sleep` 不释放锁，仅让出 CPU 一段时间。
  - 为什么wait定义在Object而不是Thread?
    - `wait/notify` 依赖对象监视器（锁）语义，操作对象锁而非线程本身。
  - 唤起指定线程？
    - `notify` 不能精确指定；可用 `Condition` 分组等待 + `signal` 定向唤醒某组线程。
  - 如何控制多个线程同时等待一个线程结束？
    - 使用 `Thread.join()`（多个线程 join 同一目标线程）或 `CountDownLatch`。

## 高频追问补充

- AQS 的 `state` 语义是否固定？
  - 不固定。不同同步器自行定义：`ReentrantLock` 表示重入次数，`Semaphore` 表示许可数，`CountDownLatch` 表示剩余计数。
- `volatile` 能否保证原子性？
  - 不能。`volatile` 只保证可见性与有序性，`i++` 仍是读改写复合操作，需 `Atomic*` 或加锁。
- `ConcurrentHashMap` 为什么比 `Hashtable` 吞吐高？
  - `Hashtable` 全表锁；`ConcurrentHashMap`（JDK8）使用 CAS + synchronized 的桶级/节点级控制，冲突范围更小。
- 为什么线程池参数不能“一套配置走天下”？
  - 任务形态不同（CPU/I-O/混合）导致最优线程数、队列容量、拒绝策略完全不同，必须压测定型。
- 线程安全集合是否一定性能低？
  - 不一定。关键看读写比与冲突模式：例如读多写少时 `CopyOnWriteArrayList` 非常高效。

## 最小示例

- Semaphore 限流（单机并发闸门）

```java
Semaphore semaphore = new Semaphore(100);
if (semaphore.tryAcquire()) {
    try {
        // 业务逻辑
    } finally {
        semaphore.release();
    }
} else {
    // 限流拒绝
}
```

- ReentrantLock + Condition 定向唤醒

```java
ReentrantLock lock = new ReentrantLock();
Condition groupA = lock.newCondition();

lock.lock();
try {
    groupA.await();
    // 被 signal 后继续执行
} finally {
    lock.unlock();
}
```

- CompletableFuture 并行汇聚

```java
CompletableFuture<String> f1 = CompletableFuture.supplyAsync(() -> callA(), pool);
CompletableFuture<String> f2 = CompletableFuture.supplyAsync(() -> callB(), pool);
String result = CompletableFuture.allOf(f1, f2)
        .thenApply(v -> f1.join() + f2.join())
        .exceptionally(ex -> "fallback")
        .join();
```

## 排查与调优清单

- 线程状态排查命令
  - `jstack <pid>`：看死锁、阻塞栈、等待点。
  - `jcmd <pid> Thread.print`：等价线程快照，线上常用。
  - `jcmd <pid> VM.native_memory summary`：辅助判断线程栈导致的内存占用。
- 线程池故障定位
  - 看 4 个核心指标：活跃线程数、队列长度、任务耗时分布、拒绝次数。
  - 业务线程池必须命名，日志要打印池名与任务标识。
  - 拒绝策略默认不建议 `Discard`，避免无日志丢任务。
- 锁竞争优化顺序
  - 减少共享数据 -> 缩小临界区 -> 锁分段/分离 -> 无锁结构（CAS）-> 异步化。

## 面试回答模板

- “先给定义，再讲机制，再讲场景，再讲风险，再给优化。”
  - 定义：该技术解决什么问题。
  - 机制：底层实现关键点（AQS/CAS/屏障/队列）。
  - 场景：在哪些业务模式使用。
  - 风险：死锁、饥饿、OOM、延迟抖动。
  - 优化：参数、结构、监控与降级策略。

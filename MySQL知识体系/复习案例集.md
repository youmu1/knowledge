## 慢 SQL / 索引

### 案例 1：隐式类型转换

- **现象**：`WHERE phone = 13800138000`（phone 为 varchar）全表扫描。
- **定位命令**：`EXPLAIN` → `type=ALL`，`key=NULL`。
- **根因**：字符串列与数字比较，列被隐式转换，索引失效。
- **解法**：改为 `WHERE phone = '13800138000'`。
- **关联**：[索引相关 § 索引失效](./索引相关.md)

### 案例 2：OR 导致索引失效

- **现象**：`WHERE a=1 OR b=2`，a 有索引 b 无，`key` 仅部分生效或 ALL。
- **定位命令**：`EXPLAIN`；`optimizer_trace`。
- **根因**：OR 一侧无法走索引，优化器可能选全表。
- **解法**：`UNION ALL` 拆两条；或给 b 加索引；评估 index merge。
- **关联**：[索引相关 § 索引失效](./索引相关.md)

### 案例 3：深分页

- **现象**：`LIMIT 1000000, 10` 数秒级延迟。
- **定位命令**：慢日志 `Rows_examined`；`EXPLAIN Extra: Using filesort`。
- **根因**：大 offset 扫描丢弃大量行。
- **解法**：`WHERE id > last_id ORDER BY id LIMIT 10`；延迟关联子查询只查 id。
- **关联**：[SQL优化 § 案例 1](./SQL优化.md)

### 案例 4：回表过多

- **现象**：有 `(status)` 索引，`SELECT *` 仍慢。
- **定位命令**：`EXPLAIN` 无 `Using index`，`rows` 大。
- **根因**：二级索引命中后逐行回表聚簇索引。
- **解法**：只查必要列；建覆盖索引 `(status, id, col1, col2)`。
- **关联**：[SQL优化 § 案例 2](./SQL优化.md)、[索引相关 § 覆盖索引](./索引相关.md)

### 案例 5：索引下推 ICP

- **现象**：联合索引 `(a,b,c)`，`WHERE a=1 AND b>2 AND c=3`，不确定 c 是否过滤。
- **定位命令**：`EXPLAIN Extra: Using index condition`。
- **根因**：5.6+ 引擎层在索引上直接过滤 c，减少回表。
- **解法**：理解 ICP 已默认优化；确保统计信息准确 `ANALYZE TABLE`。
- **关联**：[索引相关 § ICP](./索引相关.md)

## 锁 / 死锁

### 案例 6：间隙锁阻塞插入

- **现象**：RR 下 `SELECT id FROM t WHERE id>10 AND id<20 FOR UPDATE` 后，插入 id=15 等待。
- **定位命令**：`SHOW ENGINE INNODB STATUS` → `insert intention waiting`。
- **根因**：next-key lock 锁住 (10,20) 间隙防幻读。
- **解法**：预期行为；高并发插入可评估 RC；缩小锁定范围。
- **关联**：[索引相关 § 间隙锁](./索引相关.md)

### 案例 7：MDL 阻塞 DDL

- **现象**：`ALTER TABLE` 挂起，后续查询 `Waiting for table metadata lock`。
- **定位命令**：`SHOW PROCESSLIST`；查长事务 id。
- **根因**：未提交事务持有 MDL 读锁，DDL 需 MDL 写锁。
- **解法**：`KILL` 长事务；低峰 DDL；gh-ost/pt-osc。
- **关联**：[SQL优化 § 案例 3](./SQL优化.md)

### 案例 8：死锁环

- **现象**：两事务互相 `Lock wait timeout` 或 `Deadlock found`。
- **定位命令**：`SHOW ENGINE INNODB STATUS\G` → `LATEST DETECTED DEADLOCK`。
- **根因**：不同顺序更新相同行/索引间隙。
- **解法**：统一加锁顺序；小事务；重试；`SELECT ... FOR UPDATE NOWAIT` 快速失败。
- **关联**：[索引相关 § 死锁检测](./索引相关.md)

## 事务 / 日志

### 案例 9：2PC 与 binlog/redo 一致性

- **现象**：面试题「为什么先 redo prepare 再 binlog 再 redo commit？」
- **定位命令**：概念题，无命令。
- **根因**：避免「有 redo 无 binlog」或「有 binlog 无 redo」导致主从不一致。
- **解法**：背诵时序：undo → redo prepare → binlog → redo commit。
- **关联**：[日志 § 2PC](./日志.md)

### 案例 10：长事务占连接

- **现象**：连接池耗尽，活跃连接等于 pool size。
- **定位命令**：连接池 JMX；线程栈见 `@Transactional` 内 HTTP 调用。
- **根因**：事务边界过大，连接直至 commit 才归还。
- **解法**：查询移出事务；缩短边界；异步化外部调用。
- **关联**：[事务 § 案例 2](./事务.md)

### 案例 11：commit 成功但宕机丢数据

- **现象**：重启后最后一笔订单缺失。
- **定位命令**：查 `innodb_flush_log_at_trx_commit`、`sync_binlog`。
- **根因**：redo/binlog 未 fsync 即返回（配置为 2 或 0）。
- **解法**：关键业务设为 1+1；或接受风险并补偿。
- **关联**：[日志 § 案例 2](./日志.md)

## 主从 / 高可用

### 案例 12：主从延迟读旧数据

- **现象**：写主后立刻读从，查不到刚写入记录。
- **定位命令**：`SHOW SLAVE STATUS\G` → `Seconds_Behind_Master`。
- **根因**：异步复制延迟；从库单线程回放（5.6 前）或负载高。
- **解法**：写后读走主；同用户会话 sticky master；并行复制；关键读强制主库。
- **关联**：[高可用](./高可用.md)（Phase 2 详述）

### 案例 13：强制走主的实现

- **现象**：读写分离架构要求「下单后订单详情必须读主」。
- **定位命令**：代码审查 `@Transactional(readOnly)` 路由；ThreadLocal 标记。
- **根因**：默认负载均衡到从库。
- **解法**：AOP 在写后 ThreadLocal 标记本请求走主；或网关层路由 hint。
- **关联**：[高可用](./高可用.md)（Phase 2 详述）

## Java + DB 综合

### 案例 14：N+1 查询

- **现象**：列表 1000 条，DB 执行 1001 次 SELECT。
- **定位命令**：SQL 监控；MyBatis 日志；APM trace。
- **根因**：循环内按 id 单条查询，未批量 IN。
- **解法**：批量查 + Map 组装；JOIN（注意分页）；缓存。
- **关联**：[账户缓存架构优化项目](../resume-projects/账户缓存架构优化项目.md)

### 案例 15：缓存穿透打穿 DB

- **现象**：恶意查询不存在 id，DB QPS 飙升。
- **定位命令**：慢日志；Redis 命中率；不存在 key 无缓存。
- **根因**：缓存未存空值，每次 miss 查 DB。
- **解法**：空值占位 + TTL；Bloom Filter 前置。
- **关联**：[账户缓存架构优化项目 § 缓存穿透](../resume-projects/账户缓存架构优化项目.md)

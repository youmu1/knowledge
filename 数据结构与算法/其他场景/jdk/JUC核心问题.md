# JDK - JUC 核心问题

## 定义

JUC（`java.util.concurrent`）是 JDK 并发工具包，提供锁、并发容器、线程池与同步器。

## 原理

1. 通过 CAS、volatile 与队列同步器降低阻塞开销。
2. 使用 AQS 统一抽象锁与同步器实现。
3. 通过阻塞队列协调生产消费与线程调度。

## 应用场景

1. 高并发服务开发。
2. 异步任务处理。
3. 线程协作与限流。

## 面试官视角：JUC 考题设计

### 考察规则

1. 基础题考察概念边界，要求候选人能准确说明类、接口、语义和适用场景。
2. 原理题考察实现机制，要求候选人能解释 CAS、volatile、AQS、队列和线程阻塞唤醒流程。
3. 设计题考察工程取舍，要求候选人能根据吞吐量、延迟、资源上限和失败处理选择工具。
4. 排障题考察并发问题定位能力，要求候选人能识别死锁、线程池耗尽、任务堆积和内存可见性问题。

### 基础理解题

1. JUC 解决了 Java 并发编程中的哪些问题？
   - 考察点：是否能区分线程创建、线程协作、并发容器、锁、同步器、线程池等能力边界。
   - 追问方向：JUC 与 `synchronized`、`wait`、`notify` 的关系是什么？
   - 参考回答：JUC 提供了 Java 并发编程的通用工具，覆盖原子类、锁、同步器、阻塞队列、并发容器、线程池和异步编排。它不是替代基础语法，而是在 `synchronized`、`wait`、`notify` 之外提供更细粒度、更可控、更适合工程化的并发能力。

2. `volatile` 能保证什么，不能保证什么？
   - 考察点：是否理解可见性、有序性和原子性的差异。
   - 追问方向：为什么 `volatile i++` 不是线程安全操作？
   - 参考回答：`volatile` 保证变量写入后对其他线程可见，并通过内存屏障限制指令重排。它不能保证复合操作的原子性，`i++` 包含读取、加一、写回三个步骤，多个线程并发执行时会发生覆盖写，所以 `volatile i++` 不是线程安全操作。

3. CAS 的执行过程是什么？CAS 有哪些问题？
   - 考察点：是否理解比较并交换、乐观锁、自旋重试、ABA 问题和 CPU 空转成本。
   - 追问方向：`AtomicStampedReference` 如何解决 ABA 问题？
   - 参考回答：CAS 会读取内存中的当前值，与预期值比较；如果相等，就把当前值更新为新值；如果不相等，就更新失败并重试或返回失败。CAS 的问题包括 ABA 问题、自旋时间过长导致 CPU 消耗、只能直接保证单个变量更新的原子性。`AtomicStampedReference` 通过版本号判断变量是否被改动过，即使值从 A 变成 B 又变回 A，版本号也会变化。

4. `synchronized` 锁住的对象是什么？
   - 考察点：是否理解对象监视器、实例锁、类锁和代码块锁对象。
   - 追问方向：实例锁和类锁是否互斥？
   - 参考回答：`synchronized` 本质是对对象监视器加锁。修饰实例方法时锁的是当前对象 `this`；修饰静态方法时锁的是类的 `Class` 对象；修饰代码块时锁的是显式指定的对象。不同锁对象之间互不影响，因此实例锁和类锁不会互斥。

### 锁与 AQS 题

1. `ReentrantLock` 为什么支持可重入？
   - 考察点：是否理解持有线程、同步状态 `state` 和重入次数的关系。
   - 追问方向：释放锁时为什么必须将 `state` 递减到 0 才唤醒后继节点？
   - 参考回答：`ReentrantLock` 通过 AQS 的 `state` 记录重入次数，通过独占线程记录当前持锁线程。同一个线程再次获取锁时，只增加 `state`，不进入等待队列。释放锁时每次递减 `state`，只有当 `state` 归零才表示当前线程完全释放锁，此时才会唤醒后继节点。

2. AQS 如何实现独占锁？
   - 考察点：是否理解 `tryAcquire`、`addWaiter`、CLH 队列、`park`、`unpark` 的主流程。
   - 追问方向：线程入队后为什么不能立刻阻塞？
   - 参考回答：AQS 获取独占锁时先调用子类实现的 `tryAcquire`。获取失败后，线程会被包装成节点加入 CLH 同步队列，然后判断前驱节点状态，满足阻塞条件时通过 `LockSupport.park` 挂起。释放锁时调用 `tryRelease`，释放成功后通过 `unpark` 唤醒后继节点。线程入队后不能立刻阻塞，因为它需要先设置前驱节点状态，避免释放锁线程找不到需要唤醒的后继节点。

3. 公平锁和非公平锁的差异是什么？
   - 考察点：是否理解抢锁顺序、吞吐量、上下文切换和饥饿风险。
   - 追问方向：非公平锁为什么通常吞吐量更高？
   - 参考回答：公平锁获取锁前会检查同步队列中是否已有等待线程，有等待线程时按排队顺序获取锁。非公平锁允许新线程直接尝试抢锁，不严格遵守等待顺序。非公平锁通常吞吐量更高，因为减少了线程挂起、唤醒和上下文切换次数；代价是等待线程存在饥饿风险。

4. `Condition` 与 `Object.wait/notify` 的差异是什么？
   - 考察点：是否理解条件队列、同步队列和多个等待条件的隔离。
   - 追问方向：`signal` 后线程是否立即获得锁？
   - 参考回答：`Object.wait/notify` 依赖对象监视器，一个锁对象只有一个等待队列。`Condition` 依赖 `Lock`，同一个锁可以创建多个条件队列，用于区分不同等待条件。`signal` 只是把条件队列中的线程转移到同步队列，被唤醒线程还必须重新竞争锁，不能立即执行临界区代码。

### 并发容器题

1. `ConcurrentHashMap` 如何保证并发安全？
   - 考察点：是否理解 CAS、桶级锁、扩容协助、读操作无锁和写操作局部加锁。
   - 追问方向：为什么 `size()` 在并发场景下需要特殊处理？
   - 参考回答：JDK 8 的 `ConcurrentHashMap` 通过数组加链表或红黑树存储数据。读操作主要依赖 `volatile` 可见性，不加锁。插入空桶时使用 CAS，发生桶冲突时对桶头节点加 `synchronized`，扩容时多个线程可以协助迁移数据。`size()` 在并发场景下需要汇总多个计数单元，因为写操作可能同时发生，直接维护单个全局计数会成为竞争热点。

2. `CopyOnWriteArrayList` 适合什么场景？
   - 考察点：是否理解读多写少、写时复制、内存开销和最终一致读。
   - 追问方向：为什么它不适合高频写入场景？
   - 参考回答：`CopyOnWriteArrayList` 适合读多写少、数据量不大、允许读取快照数据的场景，例如监听器列表、配置快照。写入时会复制一个新数组并替换引用，读操作不加锁。它不适合高频写入，因为每次写入都有数组复制成本和额外内存占用。

3. 阻塞队列如何实现生产者消费者模型？
   - 考察点：是否理解容量约束、入队阻塞、出队阻塞和线程协作。
   - 追问方向：`ArrayBlockingQueue`、`LinkedBlockingQueue`、`SynchronousQueue` 的选型边界是什么？
   - 参考回答：生产者把任务放入阻塞队列，消费者从队列取任务。队列满时生产者阻塞或失败，队列空时消费者阻塞或失败，从而实现流量缓冲和线程协作。`ArrayBlockingQueue` 是有界数组队列，容量固定；`LinkedBlockingQueue` 是链表队列，可设置容量；`SynchronousQueue` 不存储元素，每次提交必须直接交给消费者。

### 线程池题

1. `ThreadPoolExecutor` 的核心参数有哪些？
   - 考察点：是否理解核心线程数、最大线程数、队列、拒绝策略、线程工厂和空闲回收时间。
   - 追问方向：任务提交后线程池的执行顺序是什么？
   - 参考回答：核心参数包括 `corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`workQueue`、`threadFactory`、`handler`。任务提交后，如果运行线程数小于核心线程数则创建核心线程；否则尝试进入队列；队列满且线程数小于最大线程数则创建非核心线程；仍无法处理时执行拒绝策略。

2. 为什么不建议直接使用 `Executors.newFixedThreadPool`？
   - 考察点：是否理解无界队列导致任务堆积和内存耗尽的风险。
   - 追问方向：如何根据业务流量设置有界队列和拒绝策略？
   - 参考回答：`newFixedThreadPool` 默认使用无界 `LinkedBlockingQueue`。当任务生产速度超过消费速度时，任务会持续堆积，可能导致内存耗尽。工程中需要显式创建 `ThreadPoolExecutor`，设置有界队列、线程命名、拒绝策略和监控指标。

3. 线上线程池任务堆积时如何排查？
   - 考察点：是否理解活跃线程数、队列长度、任务耗时、下游阻塞和拒绝次数。
   - 追问方向：如何区分线程数不足、任务过慢和下游依赖阻塞？
   - 参考回答：先看核心指标：活跃线程数、最大线程数、队列长度、任务执行耗时、拒绝次数、下游接口耗时。再抓线程栈，确认线程是在计算、锁等待、IO 等待还是等待下游响应。如果线程都在忙且任务耗时正常，是容量不足；如果线程长时间卡在同一调用，是任务或下游阻塞；如果队列快速增长，需要限流、降级或扩容。

### 同步器题

1. `CountDownLatch`、`CyclicBarrier`、`Semaphore` 的差异是什么？
   - 考察点：是否理解一次性倒计时、可复用屏障和许可证限流。
   - 追问方向：批量任务汇总、并行阶段推进、接口限流分别选哪个？
   - 参考回答：`CountDownLatch` 是一次性倒计时器，适合主线程等待多个子任务完成。`CyclicBarrier` 是可复用屏障，适合多个线程在阶段边界互相等待后继续执行。`Semaphore` 通过许可证控制并发数量，适合限流和资源池访问控制。批量汇总用 `CountDownLatch`，阶段推进用 `CyclicBarrier`，接口限流用 `Semaphore`。

2. `CompletableFuture` 适合解决什么问题？
   - 考察点：是否理解异步编排、回调组合、异常传播和线程池隔离。
   - 追问方向：为什么异步任务不能全部使用公共线程池？
   - 参考回答：`CompletableFuture` 适合异步任务编排，例如并行调用、串行依赖、结果合并、异常兜底和超时控制。异步任务不能全部使用公共线程池，因为公共线程池被阻塞任务占满后会影响同 JVM 内其他异步任务。业务中应按任务类型配置独立线程池，隔离 CPU 密集型任务和 IO 密集型任务。

3. `ReadWriteLock` 和 `StampedLock` 的差异是什么？
   - 考察点：是否理解读写互斥、乐观读、锁升级限制和饥饿风险。
   - 追问方向：乐观读为什么必须校验 stamp？
   - 参考回答：`ReadWriteLock` 提供读锁和写锁，多个读线程可并发，写线程与读写线程互斥。`StampedLock` 增加乐观读，读线程可以不阻塞写线程，但读取后必须校验 stamp，确认期间没有写入发生。乐观读未校验就使用结果，可能读到不一致数据。

### 场景设计题

1. 设计一个限流组件，限制同一接口每秒最多处理 100 个请求。
   - 考察点：是否能选择 `Semaphore`、令牌桶、滑动窗口或线程池隔离，并说明精度和资源成本。
   - 追问方向：当请求超过阈值时返回失败、排队等待和降级处理分别有什么影响？
   - 参考回答：单机内可以使用令牌桶或滑动窗口计数控制每秒 100 个请求；需要限制同时执行数量时可以使用 `Semaphore`。超过阈值时有三种处理规则：直接失败可以保护系统容量；短时间排队可以提高成功率但会增加延迟；降级可以返回兜底结果。生产环境还要记录通过数、拒绝数、排队耗时和接口耗时。

2. 设计一个订单异步处理线程池。
   - 考察点：是否能明确线程数、队列容量、拒绝策略、任务幂等、异常记录和监控指标。
   - 追问方向：如何保证任务失败后可追踪、可重试、不会无限堆积？
   - 参考回答：订单异步处理要使用独立 `ThreadPoolExecutor`，配置明确的核心线程数、最大线程数、有界队列、业务线程名和拒绝策略。任务必须具备幂等能力，异常要记录订单号、任务类型和失败原因。失败任务进入重试机制或补偿队列，超过重试次数后进入人工处理或告警。监控指标包括队列长度、活跃线程数、任务耗时、失败数和拒绝数。

3. 多个远程接口并行调用后聚合结果，如何实现？
   - 考察点：是否能使用 `CompletableFuture` 编排并处理超时、异常、线程池隔离和部分失败。
   - 追问方向：如果其中一个接口超时，整体结果如何返回？
   - 参考回答：可以为每个远程调用创建 `CompletableFuture`，使用独立 IO 线程池执行，通过 `allOf` 等待全部完成后聚合结果。每个任务要设置超时和异常兜底。若某个接口超时，返回规则要由业务定义：强依赖接口失败则整体失败；弱依赖接口失败则使用默认值、缓存值或缺省字段返回。

### 排障题

1. 线程池 CPU 使用率很低，但请求延迟很高，可能是什么原因？
   - 考察点：是否能定位锁竞争、阻塞 IO、下游慢调用、队列堆积和线程等待。
   - 追问方向：需要观察哪些指标和线程栈信息？
   - 参考回答：CPU 低且延迟高通常说明线程没有在计算，而是在等待。原因包括锁竞争、阻塞 IO、数据库慢查询、下游接口慢、队列堆积、连接池耗尽。需要查看线程池队列长度、活跃线程数、任务耗时、连接池指标、下游耗时和线程 dump，确认线程处于 `BLOCKED`、`WAITING` 还是网络读写等待。

2. 线上出现死锁，如何确认和修复？
   - 考察点：是否理解线程 dump、锁等待链、加锁顺序和超时释放。
   - 追问方向：如何通过锁顺序约束避免再次发生？
   - 参考回答：先通过 `jstack`、监控平台或 JVM 诊断工具获取线程 dump，查找 deadlock 信息和锁等待链，确认哪些线程持有哪些锁、等待哪些锁。修复方式包括统一加锁顺序、缩小锁范围、避免嵌套锁、使用带超时的 `tryLock`、把阻塞 IO 移出锁内。避免再次发生的核心规则是所有路径按相同顺序获取多个锁。

3. 某个共享变量偶发读取到旧值，如何分析？
   - 考察点：是否理解内存可见性、发布安全、指令重排和同步边界。
   - 追问方向：使用 `volatile`、锁、不可变对象分别能解决哪些问题？
   - 参考回答：偶发读取旧值通常与内存可见性或对象发布不安全有关。先确认写入和读取之间是否存在同步关系，例如 `volatile`、锁、线程安全容器、`final` 安全发布。`volatile` 适合解决单变量可见性和禁止重排；锁同时解决可见性和临界区互斥；不可变对象通过构造后状态不变降低共享数据风险。

## 延伸问题

1. ReentrantLock 与 synchronized 的选型边界是什么？
2. AQS 如何实现公平锁与非公平锁？

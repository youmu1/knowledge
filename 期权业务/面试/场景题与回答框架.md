# 场景题与回答框架

## 定义

场外期权面试场景题的回答框架，帮助在有限时间内给出结构化、有深度的回答。

## 原理 / 结构要素

### 通用回答框架

```
业务规则 → 数据模型 → 事件流 → 边界 case → 工程权衡
```

| 步骤 | 内容 | 时长建议 |
|------|------|----------|
| 1. 业务规则 | 先用业务语言描述规则与后果 | 30 秒 |
| 2. 数据模型 | 涉及哪些实体、字段如何变更 | 30 秒 |
| 3. 事件流 | 触发什么事件、产生什么现金流、状态如何迁移 | 60 秒 |
| 4. 边界 case | 同日触发、部分平仓、停牌、幂等 | 30 秒 |
| 5. 工程权衡 | 为什么这样设计、有何替代方案 | 30 秒 |

### STAR 变体（项目经历题）

| 要素 | 说明 |
|------|------|
| Situation | 业务背景与问题 |
| Task | 你的职责与目标 |
| Action | 技术方案（映射到框架 2~4） |
| Result | 量化结果（代码行数、bug 率、性能） |

## 业务规则

1. 每个场景题必须覆盖至少一个**边界 case**，体现工程严谨性。
2. 工程实现部分引用具体模式（Handler、StateMachine），不空谈「用了设计模式」。
3. 数字举例（名义本金、价格、Payoff）使回答更具体。
4. 回答控制在 3 分钟以内，先结论后展开。

## 工程实现要点

### 场景 1：雪球敲入后如何改状态与重算估值？

**业务规则：**
观察日收盘价 S ≤ 敲入价 B_in → 合约敲入，客户从无保护变为承担下跌风险。

**数据模型：**
`Contract.status`: LIVE → KNOCKED_IN；Event Log 写入 KNOCK_IN，Payload 含 observationPrice、barrierPrice、termsVersion。

**事件流：**
1. ObservationBatchJob 在收盘价发布后运行。
2. 判定 S ≤ B_in → 发布 KNOCK_IN 事件。
3. StateMachine 迁移状态；**不产生现金流**。
4. 触发 ValuationBatchJob 重算 NPV（Payoff 形态变化，模型切换为已敲入版本）。

**边界 case：**
- 敲入保护期内：跳过判定。
- 已 KNOCKED_OUT：跳过（已终止）。
- 幂等：contractId + KNOCK_IN + observationDate。

**工程权衡：**
敲入不生成现金流是为避免重复记账；估值与现金流解耦，由事件总线异步触发。

### 场景 2：平仓部分名义本金如何分摊现金流？

**业务规则：**
部分平仓 30% 名义本金 → 剩余 70% 继续 Live，结算金 = NPV × 30%。

**数据模型：**
`remainingNotional` -= 0.3 × initialNotional；status 仍为 LIVE（非 UNWOUND）。

**事件流：**
1. API 触发 UNWIND，Payload：`unwindRatio=0.3`、`settlementAmount=NPV×0.3`。
2. PaymentOptionHandler 生成结算现金流（30% 部分）。
3. TradeFeeHandler 生成对应比例交易费。
4. 后续 COUPON 按 remainingNotional 比例缩放。

**边界 case：**
- 部分平仓后能否敲入：可以，观察继续。
- 多次部分平仓：remainingNotional 累减，至 0 时 → CLOSED。

---

### 场景 3：OPEN 事件如何产生现金流？

**业务规则：**
开仓时买方支付期权费，可能同时产生交易费。

**数据模型：**
CashFlow 表写入两条记录：PREMIUM + TRADE_FEE，关联 eventId、contractId。

**事件流：**
1. 审批通过 → OPEN 事件。
2. CapitalFlowService 遍历 CashFlowViewDTO 列表。
3. Factory 匹配 PremiumHandler（OPEN + PREMIUM）和 TradeFeeHandler（OPEN + TRADE_FEE）。
4. 各 Handler 填充 CapitalFlowDTO 的方向与展示名。

**边界 case：**
- 期权费为 0 的结构化产品：PremiumHandler supports 返回 false，跳过。
- 重复 OPEN：幂等键拒绝。

**工程权衡：**
Factory + Handler 替代 80 行 if-else，新增现金流类型只需加 Handler 类。详见 [CapitalFlowService 重构案例](../../重构案例/CapitalFlowService%20重构案例.md)。

### 场景 4：观察日批处理失败如何保障一致性？

**业务规则：**
单合约失败不影响其他合约；失败合约进入重试队列。

**数据模型：**
LifecycleEvent.status = FAILED；retryCount++。

**事件流：**
1. 批处理按 contractId 分片，片内串行（乐观锁）。
2. 单合约 try-catch，失败写 FAILED 状态 + 告警。
3. 重试 Job 按 FAILED 事件重跑，幂等键防重复。

**边界 case：**
- 部分成功（状态已改、现金流失败）：整体事务回滚。
- 市场数据延迟：Job 延迟触发，不跑不完整数据。

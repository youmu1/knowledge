# 状态机与流程编排

## 定义

状态机管理合约在生命周期各阶段之间的合法迁移；流程编排将审批、事件处理与状态迁移串联为可追踪的业务流程。

## 原理 / 结构要素

### 状态迁移矩阵（摘要）

| 当前状态 | 允许事件 | 目标状态 |
|----------|----------|----------|
| DRAFT | SUBMIT | PENDING_APPROVAL |
| PENDING_APPROVAL | APPROVE | LIVE |
| PENDING_APPROVAL | REJECT | DRAFT |
| LIVE | KNOCK_IN | KNOCKED_IN |
| LIVE | KNOCK_OUT | KNOCKED_OUT |
| LIVE | UNWIND（全部） | UNWOUND |
| LIVE | EXPIRE | EXPIRED |
| KNOCKED_IN | UNWIND | UNWOUND |
| KNOCKED_IN | EXPIRE | EXPIRED |
| KNOCKED_OUT | SETTLE | CLOSED |
| UNWOUND | — | CLOSED |
| EXPIRED | SETTLE | SETTLED |
| SETTLED | — | CLOSED |

非法迁移：如 `CLOSED` → 任何状态、`KNOCKED_OUT` → `UNWIND`。

### 核心组件

参考 [State + Machine 模式落地实践](../../模式落地实践/State%20+%20Machine或Engine%20模式落地实践.md)：

- **State 接口**：封装当前状态下的行为。
- **StateMachine / Engine**：维护当前状态，执行 `transition(contract, event)`。
- **Context**：合约实体 + 事件 Payload。

```java
public void transition(Contract contract, LifecycleEvent event) {
    ContractStatus current = contract.getStatus();
    ContractState state = stateMap.get(current);
    state.onEvent(contract, event);  // 内部校验 + 迁移 + 副作用
}
```

## 业务规则

1. 所有状态变更必须通过 StateMachine，禁止 Service 层直接 `setStatus`。
2. 非法迁移抛 `IllegalStateTransitionException`，记录审计日志。
3. 审批节点嵌入：`DRAFT` → `PENDING_APPROVAL` 需审批通过方可 → `LIVE`。
4. 终态 `CLOSED` 不可迁移。
5. 部分 UNWIND 不改变状态（仍为 LIVE），仅更新 `remainingNotional`。
6. 状态迁移与事件写入在同一事务内完成。

## 工程实现要点

- `ContractStateMachine` 注册所有 `ContractState` 实现（Map<ContractStatus, ContractState>）。
- 每个 State 实现 `onEvent()`，内部 switch eventType 决定迁移与副作用。
- 审批流：工作流引擎（如 Camunda / 自研）驱动 PENDING_APPROVAL 节点。
- 批处理状态迁移：ObservationBatchJob 调用 StateMachine，非直接改库。
- 审计：`StateTransitionLog` 记录 from、to、event、operator、timestamp。

## 高频面试点

1. 为什么需要状态机而不是直接 UPDATE status。
2. 雪球敲入后状态如何变化、还能否敲出。
3. 非法迁移如何拦截。
4. 部分平仓为何不改变状态。
5. State 模式 vs 简单 enum switch 的选型。
6. 审批流如何与状态机集成。

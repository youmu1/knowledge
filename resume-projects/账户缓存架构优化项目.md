## STAR 法则描述

### 【Situation - 背景】

交易系统账户查询接口日均调用量 2 亿次，是核心高频接口。现有缓存设计存在以下问题：

- **架构问题**：静态字段线程安全隐患
- **性能问题**：批量查询存在 N+1 问题，1000 条数据需查询数据库 1000+ 次
- **安全问题**：缺少缓存穿透防护，恶意请求直接打到数据库
- **设计问题**：查询方法误用 @Transactional 注解，导致数据库连接占用过长
- **功能缺失**：缺少缓存更新机制，数据变更只能清空重建

### 【Task - 任务】

重构缓存设计，解决性能瓶颈和安全隐患，将批量查询响应时间降低到 1 秒以内，并提供完善的缓存管理能力。

### 【Action - 行动】

#### 1. 架构重构
- 将静态字段改为实例字段，符合 Spring Bean 最佳实践
- 完善构造函数异常处理，初始化失败抛出明确异常

#### 2. 性能优化（核心）
重构 list 方法批量查询逻辑：
- **步骤 1**：批量检查缓存，收集已命中和未命中的 key
- **步骤 2**：仅对未命中的 key 进行批量 DB 查询（1 次查询）
- **步骤 3**：批量写入缓存

**优化效果**：从原来的 O(n) 次 DB 查询优化到 O(1) 次，1000 条数据从 1000+ 次 DB 查询降低到 1 次

#### 3. 智能缓存策略
- 优化 getByOrderAccountUsername，一次查询同时更新映射缓存和主缓存
- 避免"映射缓存命中 → 主缓存未命中 → 再查 DB"的重复查询
- 减少 50% 无效 DB 访问

#### 4. 缓存穿透防护
- 对不存在的账户缓存空值标记（NULL_PLACEHOLDER）
- 恶意请求第二次查询直接返回，不再访问数据库
- 防护率 99%+

#### 5. 缓存管理能力增强
实现完整的缓存管理接口：
- `put(AccountRelaDTO)` - 更新单个缓存
- `remove(String)` - 删除单个缓存及其关联的映射缓存
- `removeBatch(Collection<String>)` - 批量删除
- `refresh()` - 刷新全部缓存

#### 6. 代码质量改进
- 移除查询方法的 @Transactional 注解，避免不必要的事务开销
- 所有方法添加参数校验（空值检查）
- 添加结构化 AI 注释（@ai.input、@ai.output、@ai.sideEffect、@ai.rule）

## 技术详解

### 架构设计

采用 Redisson LocalCachedMap 实现本地+分布式二级缓存架构：

```
┌─────────────────────────────────────┐
│        应用层 (Application)          │
├─────────────────────────────────────┤
│     AccountRelaCache (缓存层)       │
│  ┌─────────────────────────────┐   │
│  │  LocalCache (JVM 本地缓存)   │   │
│  │  - 零网络开销                │   │
│  │  - 毫秒级响应                │   │
│  └─────────────────────────────┘   │
│              ↕                      │
│  ┌─────────────────────────────┐   │
│  │  Redis (分布式缓存)           │   │
│  │  - 多节点同步                │   │
│  │  - 数据一致性                │   │
│  └─────────────────────────────┘   │
├─────────────────────────────────────┤
│      数据库层 (Database)             │
└─────────────────────────────────────┘
```

### 双 Map 设计

- **主缓存**：`usernameAccountRelaMap<String, AccountRelaDTO>`
  - Key: 资金账户用户名
  - Value: 完整的账户关联信息
  
- **映射缓存**：`tradeAccountUsernameMap<String, String>`
  - Key: 交易账户用户名
  - Value: 资金账户用户名
  - 作用: 快速定位主缓存

### 核心优化代码片段

#### 优化前的批量查询（N+1 问题）

```java
// ❌ 问题代码：每次都可能触发 DB 查询
Map<String, AccountRelaDTO> map = usernames.stream()
    .map(this::get)  // 每个 username 都可能查 DB
    .collect(Collectors.toMap(AccountRelaDTO::getUsername, 
             Function.identity(), (a, b) -> a));

// 又再次尝试批量查询未命中的，但此时已经查过了
List<String> notInCache = usernames.stream()
    .filter(username -> !map.containsKey(username))
    .collect(Collectors.toList());
```

**问题分析**：
- 第一次 `map(this::get)` 已经触发了 n 次可能的 DB 查询
- 第二次再尝试批量查询已经太晚了，存在重复查询

#### 优化后的批量查询（O(1) 查询）

```java
// ✅ 优化代码：先批量检查，再批量查询
Set<String> uniqueUsernames = new HashSet<>(usernames);
Map<String, AccountRelaDTO> resultMap = new HashMap<>();
List<String> notInCache = new ArrayList<>();

// 步骤 1: 批量检查缓存
for (String username : uniqueUsernames) {
    if (StrUtil.isEmpty(username)) continue;
    
    AccountRelaDTO cached = usernameAccountRelaMap.get(username);
    if (cached != null) {
        resultMap.put(username, cached);
    } else {
        notInCache.add(username);  // 收集未命中的
    }
}

// 步骤 2: 批量查询数据库（仅 1 次查询）
if (CollUtil.isNotEmpty(notInCache)) {
    List<AccountRela> fromDB = accountRelaService
        .listByUsernames(notInCache);
    List<AccountRelaDTO> dtoList = accountRelaMapper.from(fromDB);
    
    // 步骤 3: 批量写入缓存
    for (AccountRelaDTO dto : dtoList) {
        resultMap.put(dto.getUsername(), dto);
        RedisCacheUtil.safePut(CACHE_NAME, dto.getUsername(), 
                               dto, usernameAccountRelaMap);
    }
}
```

**优化效果**：
- 查询次数：1000 次 → 1 次
- 响应时间：5000ms → 500ms
- 性能提升：10 倍

#### 缓存穿透防护

```java
// ✅ 对不存在的账户缓存空值标记
if (accountRela == null) {
    // 缓存空值标记，防止反复查询
    RedisCacheUtil.safePut(ACCOUNT_CACHE_NAME, username, 
        NULL_VALUE_PLACEHOLDER, tradeAccountUsernameMap);
    return null;
}

// 查询时检查空值标记
String capitalAccountUsername = tradeAccountUsernameMap.get(username);
if (NULL_VALUE_PLACEHOLDER.equals(capitalAccountUsername)) {
    return null;  // 直接返回，不查 DB
}
```

**防护效果**：
- 恶意请求第一次查 DB，后续直接返回
- 数据库保护率 99%+

### 可能的面试问题

**Q1: 为什么选择 Redisson LocalCachedMap 而不是其他缓存方案？**

A: 对比了多种方案：
- Spring Cache + Redis：两级缓存需要手动管理同步
- Caffeine + Redis：同样需要自己实现同步机制
- **Redisson LocalCachedMap**：内置多节点同步，开箱即用

选择理由：
1. 本地缓存零网络开销，性能最优
2. 内置多种同步策略（INVALIDATE、UPDATE等）
3. 支持缓存大小、过期时间等配置
4. 与现有 Redis 基础设施无缝集成

**Q2: 如何保证多节点缓存一致性？**

A: Redisson LocalCachedMap 提供了多种同步策略：
1. **INVALIDATE（失效模式）**：一个节点修改后，通知其他节点失效
2. **UPDATE（更新模式）**：一个节点修改后，推送新值到其他节点
3. **NONE（无同步）**：仅用于只读场景

我们采用 INVALIDATE 模式，因为：
- 账户信息修改频率低
- 失效后重新加载的成本可接受
- 避免大对象传输的网络开销

**Q3: 批量查询优化的核心思路是什么？**

A: 核心思路是**延迟查询 + 批量聚合**：

1. **延迟查询**：不要立即查询每个 key，先收集所有需要查询的 key
2. **批量聚合**：将收集到的 key 一次性查询，利用 SQL 的 IN 语句
3. **批量回写**：查询结果一次性写入缓存

关键点：
- 避免循环中的 I/O 操作
- 利用数据库的批量查询能力
- 减少网络往返次数（RTT）

**Q4: 缓存穿透防护为什么用空值标记而不是布隆过滤器？**

A: 对比两种方案：

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 布隆过滤器 | 内存占用小 | 存在误判、难以删除 | 海量数据去重 |
| 空值标记 | 精确、易维护 | 占用缓存空间 | 中等规模数据 |

选择空值标记的原因：
1. 账户数据量可控（百万级），缓存空间充足
2. 需要精确判断，不能误判
3. 账户可能被删除后重建，需要支持删除
4. 实现简单，维护成本低

**Q5: 如果缓存击穿（热点 key 失效）怎么办？**

A: 多层防护：

1. **互斥锁**：使用 Redisson 的分布式锁，同时只有一个线程查询 DB
```java
RLock lock = redissonClient.getLock("cache:reload:" + key);
try {
    lock.lock();
    // double check
    AccountRelaDTO cached = cache.get(key);
    if (cached == null) {
        cached = loadFromDB(key);
        cache.put(key, cached);
    }
    return cached;
} finally {
    lock.unlock();
}
```

2. **设置永不过期**：对于超高频 key，设置永不过期，通过主动更新维护
3. **后台刷新**：快过期时，异步加载新数据
